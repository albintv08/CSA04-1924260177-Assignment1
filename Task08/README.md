# TASK 8 – EVALUATE CPU STATES AND PROTECTION

## 1. Introduction

Hardware protection is essential in a smart hospital because bedside monitors continuously measure patient parameters such as heart rate, blood pressure, oxygen saturation and body temperature. The operating system and processor must ensure that applications cannot interfere with critical monitoring operations, access unauthorised data or prevent urgent events from being handled.

The CPU provides protection through user mode, kernel mode, privileged instructions, interrupts, traps, timer interrupts and memory protection mechanisms.

## 2. User Mode and Kernel Mode

Modern processors operate using two main execution modes:

**User Mode:**
- Used by ordinary applications, such as hospital dashboards and patient-record applications.
- Applications have restricted access to hardware and critical system resources.
- They cannot directly execute privileged instructions.
- They must request operating-system services through system calls.

**Kernel Mode:**
- Used by the operating-system kernel.
- Allows access to hardware, memory-management functions, device controllers and interrupt-handling mechanisms.
- Can execute privileged instructions required to manage system resources.

**Privileged instructions** are special CPU instructions that can only be executed in kernel mode. Examples include disabling interrupts, changing memory-management settings and controlling certain hardware devices.

The **mode bit** is a hardware indicator that identifies the current execution mode. When a program makes a system call or an interrupt occurs, the processor switches from user mode to kernel mode. After the operation is completed, control can return to user mode.

**Application to hospital monitors:** A patient-monitoring application can collect and display sensor readings, but it cannot directly change critical processor settings or disable hardware protection. The operating system controls access to these resources.

## 3. Interrupts, Traps and Timer Interrupts

### Interrupts

An interrupt is a signal that requests the CPU's attention from a hardware device or controller. It allows the processor to respond to important events without continuously checking every device.

For example, a bedside monitor may generate an interrupt when a sensor detects an abnormal reading. The processor temporarily pauses its current activity, executes the appropriate interrupt handler and processes the event.

### Traps

A trap is a software-generated or processor-detected exception that transfers control to the operating system. It may occur because of a system call, an invalid operation or an error such as division by zero.

For example, when a hospital application requests access to a protected file, it uses a system call that transfers control to the kernel.

### Timer Interrupts

A timer interrupt is generated by a hardware timer at regular intervals. It allows the operating system to regain control of the CPU and perform scheduling activities.

It helps the operating system:
- Prevent one application from occupying the CPU indefinitely.
- Switch between running processes.
- Schedule high-priority monitoring tasks.
- Maintain system responsiveness.

**Evaluation:** Interrupts provide faster event-driven responses than continuously checking devices. Traps provide controlled access to operating-system services, while timer interrupts ensure that the operating system retains control of CPU execution.

## 4. What Happens If Any Program Can Disable Interrupts?

If every application were allowed to disable interrupts, the hospital monitoring system would become unreliable and potentially dangerous.

Possible consequences include:

1. **Delayed emergency detection:** A program could prevent the CPU from responding immediately to an abnormal sensor reading.
2. **Missed monitoring events:** Important hardware notifications could be delayed while interrupts remain disabled.
3. **System unresponsiveness:** The operating system might not receive timer interrupts and could fail to schedule other processes properly.
4. **Patient safety risks:** Critical warnings about abnormal heart rate or oxygen levels could be delayed.
5. **Denial of service:** A faulty or malicious application could disable interrupts continuously and prevent normal system operation.

Therefore, disabling interrupts must be restricted to authorised kernel operations. Even the kernel should keep interrupt-disabled periods as short as possible, especially in real-time monitoring systems.

## 5. How Hardware Prevents One Program from Reading Another Program's Memory

The processor uses hardware memory-protection mechanisms, commonly through a Memory Management Unit (MMU), to isolate processes.

The MMU translates virtual addresses into physical addresses and checks whether a process has permission to access a memory location.

Important protection mechanisms include:

- **Process isolation:** Each process receives its own virtual address space.
- **Memory permissions:** Memory pages can be marked as readable, writable or executable.
- **Access checking:** The MMU checks whether a memory access is permitted.
- **Protection faults:** If a program attempts unauthorised access, the processor generates an exception and transfers control to the operating system.
- **Kernel memory protection:** User applications cannot directly access protected kernel memory.

**Hospital application:** A patient-monitoring application should not be able to read another application's private memory or access confidential patient information without authorisation. Memory protection reduces the possibility of accidental data corruption and unauthorised access.

## 6. Alternative Concept and Complexity Analysis: Polling Versus Interrupts

If bedside monitors used polling instead of interrupts, the CPU would repeatedly check the sensor at fixed time intervals to determine whether a new reading or abnormal condition had occurred.

For example, a monitoring program could check a sensor every 10 milliseconds.

### Polling approach

- The CPU repeatedly checks the sensor.
- If an abnormal reading occurs immediately after a check, the system may not detect it until the next check.
- Short polling intervals improve detection time but increase CPU activity and power consumption.
- Long polling intervals reduce CPU activity but may delay emergency detection.

### Worst-case detection delay

Let:

- \(T\) = polling interval
- \(L\) = interrupt response latency

For polling, the worst-case detection delay is approximately:

\[
D_{\text{poll,max}} = T
\]

The average detection delay, assuming the event can occur at any time within the polling interval, is approximately:

\[
D_{\text{poll,avg}} = \frac{T}{2}
\]

For interrupt-driven monitoring, the event is detected and serviced after the hardware interrupt response latency:

\[
D_{\text{interrupt}} \approx L
\]

This assumes the interrupt is enabled and not delayed by higher-priority interrupts or other system activity.

### Example comparison

Assume a sensor is checked every 10 milliseconds and the interrupt response latency is 0.1 milliseconds.

| Parameter | Polling | Interrupt |
|---|---:|---:|
| Checking interval | 10 ms | Event-driven |
| Worst-case detection delay | 10 ms | Approximately 0.1 ms |
| Average detection delay | 5 ms | Depends on interrupt handling |
| CPU usage | Repeated checking | CPU can perform other work while waiting |
| Power consumption | Can be higher | Often lower during idle periods |

### CPU time and power wasted by polling

If the CPU spends \(C\) milliseconds checking a sensor every \(T\) milliseconds, the approximate fraction of CPU time spent polling is:

\[
\text{CPU usage} = \frac{C}{T}\times 100\%
\]

For example, if checking takes 0.2 ms and the polling interval is 10 ms:

\[
\frac{0.2}{10}\times100 = 2\%
\]

This means approximately 2% of CPU time is spent checking the sensor, even when no abnormal reading is present. Repeated polling across many sensors can increase CPU load and energy consumption.

### Evaluation and preferred solution

For hospital bedside monitors, interrupt-driven monitoring is generally preferable because it allows the processor to respond to important sensor events without continuously checking the devices.

However, interrupts must be supported by suitable real-time scheduling, bounded interrupt-handling time and reliable alarm-processing software. Polling may still be useful for non-critical periodic checks or when a device does not support interrupts.

## 7. Conclusion

CPU states and hardware protection mechanisms are essential for maintaining the safety, security and reliability of a smart hospital. User mode and kernel mode restrict access to critical operations, while privileged instructions prevent ordinary applications from controlling protected hardware functions. Interrupts and timer interrupts support timely event handling and CPU scheduling. The MMU protects the memory of individual processes from unauthorised access.

For bedside patient monitors, interrupt-driven processing is generally more suitable than continuous polling because it reduces unnecessary CPU activity and can provide faster responses to abnormal readings. These hardware protection mechanisms help ensure that critical patient-monitoring operations remain reliable.
